# Prizmatic Backend

NestJS 11 backend for Prizmatic, a project collaboration system for workspaces,
projects, sprints, work items, comments, documents, notifications, agent runs,
and embedding jobs.

## Current Problem Statement

Prizmatic helps software teams organize project work in one workspace. The
backend provides authentication, workspace membership, project planning, sprint
tracking, work item collaboration, document storage metadata, realtime
notifications, and internal service APIs used by automation and embedding
workers.

## Supported Developer Environments

These instructions are intended for the operating systems used by the team and
CI:

- macOS 14+ with Homebrew
- Ubuntu 22.04+ or another recent Linux distribution
- Windows 11 using WSL2 Ubuntu, or Windows PowerShell with Node.js and pnpm
  installed
- GitHub Actions CI on Ubuntu with Node.js 22

Use Node.js 22 and pnpm. The CI workflow installs Node 22 and runs the same
verification commands listed below.

macOS, Linux, and WSL2:

```bash

```

Windows PowerShell:

```powershell
corepack enable

```

Do not commit `.env`. It is intentionally local and may contain secrets.

## Environment Configuration

The application validates configuration at startup in
`src/core/config/env.validation.ts`. Important local settings:

- `PORT`: HTTP port. Defaults to `3000`.
- `APP_NAME`, `APP_DESCRIPTION`, `APP_VERSION`: values shown in Swagger.
- `JWT_SECRET`, `JWT_REFRESH_SECRET`: token signing secrets. Use stronger
  values outside local development.
- `CORS_ORIGIN`: comma-separated allowed frontend origins. Leave blank for open
  local development.
- `DB_ENABLED`: set to `true` for the real feature modules.
- `PG_HOST`, `PG_PORT`, `PG_USER`, `PG_PASSWORD`, `PG_DB`, `PG_SCHEMA`:
  PostgreSQL connection settings.
- `EMAIL_ENABLED`, `QUEUE_ENABLED`, `OBJECT_STORAGE_ENABLED`: optional OCI
  integrations. Leave them `false` for normal local API development unless you
  are testing those integrations.

When `DB_ENABLED=false`, the app still starts and exposes health, readiness, and
Swagger, but DB-backed feature modules are not registered. Use
`DB_ENABLED=true` for full local testing.

## Database Setup

The backend uses PostgreSQL and TypeORM migrations. TypeORM `synchronize` is
disabled, so schema changes must come from migrations.

Option A: local PostgreSQL service

1. Install PostgreSQL 15+ using Homebrew, apt, or the Windows installer.
2. Create a development database.

```bash
createdb your_local_database
```

3. Update `.env`.

```text
DB_ENABLED=true
PG_HOST=127.0.0.1
PG_PORT=5432
PG_USER=postgres
PG_PASSWORD=postgres
PG_DB=your_local_database
PG_SCHEMA=
```

4. Run migrations.

```bash
pnpm run migration:run
```

Option B: Docker PostgreSQL

```bash
docker run --name prism-postgres \
  -e POSTGRES_USER=postgres \
  -e POSTGRES_PASSWORD=postgres \
  -e POSTGRES_DB=your_local_database \
  -p 5432:5432 \
  -d postgres:16
```

Then use the same `.env` values and run `pnpm run migration:run`.

## Run The API Locally

Start the development server:

```bash
pnpm run start:dev
```

The API runs at `http://localhost:3000` unless `PORT` is changed.

Useful local URLs:

- `GET http://localhost:3000/health`: process liveness
- `GET http://localhost:3000/ready`: readiness, including database readiness
  when `DB_ENABLED=true`
- `http://localhost:3000/docs`: Swagger API documentation
- `http://localhost:3000/docs-json`: OpenAPI JSON generated by Swagger

## Build The Software

```bash
pnpm run build
```

The compiled output is written to `dist/`. Do not edit files in `dist/`
directly.

Run the built app:

```bash
pnpm run start:prod
```

Docker build:

```bash
docker build -t prism-nestjs .
docker run --env-file .env -p 3000:3000 prism-nestjs
```

## Test The Software

Run these checks before opening or merging a pull request:

```bash
pnpm run lint:check
pnpm run build
pnpm run test -- --runInBand
pnpm run test:e2e -- --runInBand
```

Current automated coverage is light. The existing e2e test covers health and
readiness without requiring the full database-backed application. For manual
feature testing, set `DB_ENABLED=true`, run migrations, start the API, and use
Swagger at `/docs` to exercise the feature endpoints.

Run formatting after changing TypeScript files:

```bash
pnpm format
```

## API Design Documentation

Swagger is the canonical backend API design document for this repository. Start
the API with `DB_ENABLED=true` and open:

- `http://localhost:3000/docs`
- `http://localhost:3000/docs-json`

The documented API currently covers these groups:

- Authentication and onboarding
- User preferences
- Workspaces, members, invitations, roles, and jobs
- Workspace feature provisioning
- Projects, work items, comments, and realtime project updates
- Sprints and sprint work item scheduling
- Project documents and document chunks
- Notifications and realtime notification delivery
- Agent runs, actions, memories, and event streams
- Embedding jobs and internal worker APIs
- Admin service tokens, audit events, and embedding health checks

When an endpoint, DTO, response shape, or auth requirement changes, update the
controller and DTO Swagger decorators in the same pull request and verify the
change in `/docs` before marking the API task complete.

## Project Schedule

Detailed assignments should be tracked in GitHub Issues or the team's project
board. This README keeps the public milestone summary updated for check-ins.
Course due dates come from the official course schedule.

| Milestone | Status | Completed items | Remaining or adjusted items |
| --- | --- | --- | --- |
| Milestone 1 | Completed | Repository setup, NestJS baseline, health/readiness endpoints, CI commands, initial README setup instructions | Keep setup docs current as environment requirements change |
| Milestone 2 | Completed | Authentication foundation, onboarding, workspace and project API structure, PostgreSQL migration flow | Continue refining auth and workspace edge cases through bug reports |
| Milestone 3 | Completed | Work item APIs, comments, notifications, document metadata, service token foundation, embedding job foundation | Expand manual verification for completed features and record bugs in GitHub Issues |
| Milestone 4 beta | In progress | Sprint APIs, sprint work item management, mention notifications, feature provisioning requests, admin/worker API hardening, deployment workflow | Finish beta deployment verification, update the Milestone 4 Progress Update document, and triage serious bugs before final release |
| Final release | Planned | Not started | Stabilize core workflows, complete non-implementer verification for all completed features, fix serious bugs, update API docs, run full checks, and prepare final demo |

Schedule adjustments made for the beta:

- Agent, embedding, document, and feature provisioning workflows are treated as
  beta features until integration testing is complete.
- Final-release time is reserved for bug fixing and verification instead of
  adding large new feature areas.
- Serious bugs must be assigned in GitHub Issues and accounted for in the final
  release schedule before new polish work is started.

## Weekly Milestone Check-In

Before each instructor check-in:

1. Pull the latest `develop` branch.
2. Confirm the README, API docs, schedule, and bug tracker are current.
3. Run or review the latest CI checks.
4. Demo the completed work from the local API, the beta deployment, or Swagger.
5. Each team member should be ready to state what they completed last week,
   what they plan to do this week, and any blockers.

## Beta Release Notes

Milestone 4 is the beta release checkpoint. The beta should be accessible from
the team's deployed API link. The deployment workflow in
`.github/workflows/deploy.yml` builds the Docker image, pushes it to GHCR, and
deploys it to OCI when a pull request is merged into `develop` or when the
workflow is manually triggered.

For the Milestone 4 Progress Update document, include:

- Each member's scheduled tasks and in-progress tasks.
- Each member's actually completed tasks.
- Partial tasks with completion percentages.
- A group comparison between the original schedule and current beta status.
- The team's progress grade and the reason for that grade.
- Delays, blockers, serious bugs, and schedule adjustments for final release.

## Bug Tracking And Verification

Outstanding bugs are tracked in GitHub Issues:

https://github.com/prism-416/prism-nestjs/issues

To report a bug:

1. Open a new GitHub Issue.
2. Use a clear title that names the affected feature.
3. Include reproduction steps, expected behavior, actual behavior, environment
   details, screenshots or logs when useful, and severity.
4. Add labels such as `bug`, `backend`, `api`, or the relevant feature label.
5. Assign serious bugs to a team member and account for the fix in the project
   schedule.

For every feature marked complete, someone who did not implement that feature
should verify it through Swagger, the frontend, or an API client. Any issue found
during verification should be filed in GitHub Issues before the feature is
considered ready for final release.
